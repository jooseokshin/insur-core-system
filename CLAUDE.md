# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Tests

Spring Boot 4 splits the test slices out of the old monolithic `spring-boot-starter-test` into `spring-boot-starter-data-jpa-test` and `spring-boot-starter-webmvc-test`, so slice annotations (`@DataJpaTest`, `@WebMvcTest`) live in modularized packages that differ from Boot 3.

## Configuration

`application.properties` points the datasource at the docker-compose Postgres by default. You can override it with the `DB_URL`, `DB_USERNAME` and `DB_PASSWORD` environment variables. Because the app connects to a real database, `bootRun` and the `@SpringBootTest` `contextLoads` test both need `docker compose up -d` first. The DB runs in Asia/Seoul time and Hibernate's `jdbc.time_zone` matches it, so keep the two consistent. `main` also forces the JVM default time zone to Asia/Seoul, because Hibernate converts `LocalDateTime` through the JVM zone before applying `jdbc.time_zone` (a UTC JVM would store timestamps 9 hours off), and the `test` task runs in that zone too. Timestamps and numbering years come from the injected business `Clock` bean (`BusinessClockConfig`), not `LocalDateTime.now()`.

All endpoints require a JWT Bearer token. Production tokens are RS256, issued by the auth server and verified against its public keys (`app.jwt.jwk-set-uri` = `JWK_SET_URI`, e.g. `http://auth:8081/auth/oauth2/jwks`) with an exact issuer match (`app.jwt.issuer` = `AUTH_ISSUER`, the browser-facing origin; required when the JWKS URI is set). HS256 tokens are accepted only when `app.jwt.secret` (`JWT_SECRET`, at least 32 bytes) is set, which is for dev tokens (`scripts/dev-token.sh`, `scripts/e2e-check.sh`) and tests; leave it empty in production because whoever holds the secret can mint tokens. `AlgorithmRoutingJwtDecoder` picks the verifier by the `alg` header and rejects anything else (including `none`), and startup fails when neither is configured. For local runs, activate the `local` profile (`SPRING_PROFILES_ACTIVE=local`, or Active profiles in the IDE run configuration): `application-local.properties` sets the public dev-only HS256 key (`${JWT_SECRET:<dev key>}`) plus the local auth server's JWKS (`http://127.0.0.1:8081/auth/oauth2/jwks`) and issuer (`http://127.0.0.1:5173`); everything else comes from `application.properties`. The token's `sub` claim becomes the request's `empId` and overrides whatever the client sent in the message header. Never activate `local` in production. The core `test` task injects its own `JWT_SECRET` in `build.gradle` (most tests use HS256 or the `jwt()` post-processor; `RsaJwtAuthenticationTest` serves a JWKS from an in-process HTTP server). Roles come from the token's `roles` claim (string array: `AGENT`, `UNDERWRITER`, `OPERATOR`, `ADMIN`, mapped to `ROLE_` authorities). Per-API roles are URL rules in `SecurityConfig`, and the target-status check for `/status-change` is `ContractAccessPolicy`. Data-level scope: a caller whose only role is `AGENT` can inquire only contracts they received (`REG_EMP_ID` = token `sub`); other callers see all, and a contract outside the scope answers exactly like a missing one (404 `E-CTR-010`). Premium quotes (`POST /api/premium/quote`) compute `isrdAmt × annual rate × days ÷ 365` from the `TB_PRM_RATE` table, whose seeded rates (V7) are sample values for development, not a real tariff; change them with a new migration. `POST /api/contract/apply` verifies each coverage `prem` against that same calculation for new applications (E-CTR-020; replays of an already-accepted `globalTxId` skip the check), so test data and clients must use premiums consistent with the rate table. Rating factors (`TB_PRM_FACTOR`, optional `rating` input: `driverAge`, `discountGrade`, `structureGrade`) multiply the base rate, and rates/factors are effective-dated (`EFF_FROM`..`EFF_TO` inclusive, looked up by the policy start date): to revise a tariff, close the old row's `EFF_TO` and add a new row in a new migration; a trigger rejects overlapping periods. Termination (`status-change` to 30) records the termination date and a pro-rata refund premium; `/endorse` changes the policyholder/insured of a contract in status 10 or 20 and keeps an audit row per changed field. Payment: `POST /api/contract/payment` (OPERATOR/ADMIN) records a payment on a status-10 contract (installments allowed, `TB_CTR_PAYMENT`, V18; overpaying the remaining premium is E-CTR-027, idempotent per `globalTxId`), and `status-change` to 20 (approval) is rejected with E-CTR-028 until the paid total reaches the contract's total premium; tests that approve contracts must pay in full first. `POST /api/contract/payment-history` lists payments with the paid/remaining totals. `status-change` and `endorse` are idempotent per (contract, `globalTxId`): a replay returns the first result and a different request under the same id is E-CTR-019. The tariff is managed through `/api/admin/premium/{rate,factor}-{list,revise}` (list: UNDERWRITER/OPERATOR/ADMIN, revise: ADMIN only): a revise closes the latest row at `effFrom - 1` and inserts the new row, the new start date must be today (Seoul) or later and after the latest row's start, every change is written to `TB_PRM_AUDIT`, and a replay of the same `globalTxId` returns the first result. `/api/admin/premium/audit-list` (UNDERWRITER/OPERATOR/ADMIN) pages through `TB_PRM_AUDIT`, newest first, filtered by targetType, targetKey prefix, empId and a Seoul-date range. `POST /api/contract/renew` (AGENT own contracts / ADMIN) renews an in-force (20) contract from 60 days before its end date through the end date: it creates a new application (status 10) starting at the old end date with the same term, parties and coverages, re-quotes premiums at renewal time (rating from the request, else the old contract's stored values), and links it through `RENEWED_FROM`; a partial unique index (V17) allows one non-cancelled renewal per contract (E-CTR-025), and replays of the same `globalTxId` return the first result. `POST /api/contract/renew-quote` previews the same renewal (same checks, roles and quote, nothing saved) with the premium difference against the old contract. API docs come from springdoc (`build.gradle`, version 3.x for Boot 4): Swagger UI at `/swagger-ui.html` and the spec at `/v3/api-docs` are open without a token (GET only, `SecurityConfig`), the Authorize button takes a Bearer token from `scripts/dev-token.sh`, they are off by default (`springdoc.*.enabled=${API_DOCS_ENABLED:false}`), the `local` profile turns them on, and elsewhere `API_DOCS_ENABLED=true` is needed. Field descriptions come from `@Schema(description = ...)` on every DTO field and endpoint summaries from `@Operation`/`@Tag` on the controllers; when you add a DTO field or endpoint, keep the javadoc and the annotation text in sync. `scripts/dev-token.sh [empId] [ttlSeconds] [roles]` issues a local dev token (roles default to `ADMIN`). `scripts/e2e-check.sh [--cleanup]` runs an end-to-end check (auth, roles, apply, inquiry, status change, history) against a running app with the same `JWT_SECRET`; it writes real rows to the dev DB, so use `--cleanup` to remove them.

## Work APIs (core)

`/api/work/dashboard`, `/api/work/todo` and `/api/work/renewal-targets` (`WorkController`, `WorkService`) back the staff screens. They are read-only aggregates written as SQL with `NamedParameterJdbcTemplate`, open to all four roles, and an AGENT-only caller is limited to their own contracts like the other inquiry APIs. To-do types (`TodoType`) carry their own roles: PENDING_APPROVAL (status 10, paid in full) for UNDERWRITER/ADMIN, UNPAID (status 10, not paid in full) for AGENT/OPERATOR/ADMIN, STALE_APPLICATION (status 10 for 7+ Seoul days) for AGENT/UNDERWRITER/ADMIN; asking for a type the caller cannot handle is 403 `E-AUTH-002`, an unknown type `E-WRK-001`. The dashboard only returns counts for the types the caller can see. Renewal targets are in-force contracts whose end date is within `withinDays` (1..60, default 60, `E-WRK-002` otherwise) and that have no non-cancelled renewal, the same rule as the V17 index. V19 adds the indexes these queries use.

## Products (core)

V20 adds products (`TB_PRD`, sale period `SALE_FROM`..`SALE_TO` inclusive) and their coverage composition (`TB_PRD_CVRG`: `MAIN` coverages are always required, `RIDER` coverages are optional unless marked required, each with an insured-amount range and a deductible used by claims). Products are managed by migrations only and listed through `POST /api/product/list` (`insrClsCd`, `onSaleOnly`, `prdCd`). `prdCd` is optional on `/api/premium/quote` and `/api/contract/apply`: when present, `PremiumService.quote` validates the composition (`E-PRD-001` unknown, `002` other class, `004` coverage not in product, `005` missing required, `006` amount out of range) and new business also requires the product to be on sale today (`E-PRD-003`, checked by `quoteNewBusiness` and in `applyContract` when it is not a renewal). Without `prdCd` an application is accepted exactly as before and stored with `PRD_CD` null (the legacy channel path that existing tests and `scripts/e2e-check.sh` use); keep that path working. Renewals carry the source contract's product and skip the sale-period check. `prdCd` is part of the request fingerprint only when present, so old replays keep matching.

## Claims (core)

V21 adds claims (`TB_CLM`), per-coverage claimed/assessed/deductible/paid amounts (`TB_CLM_CVRG`) and an append-only history (`TB_CLM_HIST`, unique per (claim, `globalTxId`)). Status: 10 reported → 20 assessed (awaiting payment, can be re-assessed) → 40 paid, 10/20 → 80 denied (reason required, `E-CLM-007`), 10 → 90 withdrawn. `POST /api/claim/report` (AGENT own contracts, CLAIM, ADMIN) accepts an in-force or terminated contract (`E-CLM-002` otherwise) when the accident date is within coverage: start date inclusive to min(end date, termination date) exclusive, matching the refund rule, and not in the future (`E-CLM-003`), for coverages the contract holds (`E-CLM-004`); it is idempotent per `globalTxId` with a fingerprint (`E-CLM-009` for different content). `assess` (CLAIM/ADMIN) computes pay = min(max(assessed − product deductible, 0), insured amount − already paid on that coverage by other paid claims of the contract); contracts without a product have no deductible. `decide` takes PAY/DENY (CLAIM/ADMIN) or WITHDRAW (also AGENT); paying more than `ClaimService.HIGH_VALUE_THRESHOLD` (10,000,000) needs ADMIN (`E-CLM-008`), a zero payout must be denied instead (`E-CLM-011`), and the remaining limit is re-checked at payment (`E-CLM-012`, re-assess). Assess and pay lock the contract row so two claims cannot spend the same limit. Assess/decide replays of the same (claim, `globalTxId`) return the current claim without reprocessing. A contract with an open claim (10/20) cannot be terminated (`E-CTR-030`). The `CLAIM` role (core `Roles`, auth server V2) also reads contracts, products and the dashboard, which adds a `claims` block for AGENT/CLAIM/ADMIN. Claim numbers use `TB_CMN_SEQ` with type `CLM` (`CLM-CAR-2026-000001`).

## Loss ratio (core)

`POST /api/stats/loss-ratio` (`StatsController`, `LossRatioService`, UNDERWRITER/CLAIM/ADMIN) is a read-only `NamedParameterJdbcTemplate` aggregate over `fromDate`..`toDate` inclusive (default Jan 1 of this Seoul year to today; `from > to` or a period of 5+ years is `E-STAT-001`) grouped by `groupBy` = `PRODUCT` (default), `COVERAGE` or `CLASS` (`E-STAT-002` otherwise). Earned premium is each coverage premium × (days the contract covered inside the period) ÷ term days, counting contracts in status 20/30 and ending coverage at min(end date, termination date) exclusive, the same rule as refunds and claims. Losses are accident-year: claims whose accident date is in the period, paid = status 40 `PAY_AMT`, outstanding = status 20 `PAY_AMT` + status 10 `CLAIM_AMT`; 80/90 are excluded and there is no IBNR, so recent periods understate the ratio. `lossRatio` = incurred ÷ earned (scale 4, null when earned is 0); the total row is aggregated separately so a contract counted under several coverages is counted once. `scripts/dev-data.sh [count] | --cleanup` fills the local dev DB with deterministic sample contracts, payments, terminations and claims numbered `GEN-` (it refuses non-local databases unless `DEV_DATA_FORCE=1`); never run it against a shared database.

## Rate impact simulation (core)

`POST /api/stats/rate-impact` (`RateImpactService`, UNDERWRITER/ADMIN, saves nothing; covered by the `/api/stats/**` rate-limit rule) takes `insrClsCd` (required, must have a tariff effective today, else `E-STAT-003`), an experience period (default the 12 months ending today; validated by `LossRatioService`, `E-STAT-001`), optional `targetLossRatio` (0 < t <= 1.5, `E-STAT-005`), `renewalWindowDays` (1..365, default 365, `E-STAT-006`) and `changes` (per coverage of today's tariff, -50..+100 %, at most 2 decimals, no duplicates, `E-STAT-004`; omitted coverages are 0 %). Per coverage and for the class total it returns the experience from the loss-ratio definition (reused, not re-implemented), the loss ratio had premiums been `1 + pct` higher (premium is proportional to the base rate), the loss-ratio-method indication `LR / target - 1`, limited-fluctuation credibility `Z = min(1, sqrt(n / 1082))` (1082 = (1.645 / 0.05)^2, 90 % probability within ±5 %) with `Z × indication` (complement: no change), today's in-force contracts/premium, and the renewal impact `premium × pct` for in-force contracts ending within the window that have no non-cancelled renewal (same rule as renewal targets). The total's change is the earned-premium-weighted average and its contract and claim counts are distinct. It does not model trend, IBNR/development, expenses, price elasticity or on-leveling; `warnings` flags rate/factor revisions inside the period (not on-leveled) or scheduled after today, periods within the last 90 days (IBNR), and claim counts below 1082. `RateImpactIntegrationTest` uses its own class `99` and tariff rows so shared dev data does not change its hand-computed numbers.

## Rate limiting

Two layers. nginx (`frontend/nginx/default.conf`) limits per client IP as a flood ceiling only (`/api` and `/auth` 50 r/s burst 100, `POST /auth/login` 30 r/min burst 30) and answers 429 `E-CMN-011` in the common envelope; it is deliberately loose because staff often share one office NAT/proxy IP, and behind a load balancer `set_real_ip_from` must be configured first. The core limits per employee (token `sub`) in `common/ratelimit`: `RateLimitFilter` runs inside the security chain right after `BearerTokenAuthenticationFilter` (it is not a `@Component`, so it is not registered twice), counts only authenticated `/api/**` calls (forbidden calls count too), and answers 429 `E-CMN-010` with `Retry-After`; allowed calls carry `X-RateLimit-Remaining`. Limits are token buckets from `app.rate-limit.*` (`defaults` 60 burst / 300 per minute; `rules[n]` with `name`, `paths`, `capacity`, `per-minute`, first match wins and each rule has its own bucket; `/api/stats/**` is 10 / 20). Buckets live in memory (`InMemoryRateLimitStore`, integer token math on `nanoTime`), so N instances allow N times the limit; to share limits, register another `RateLimitStore` bean (e.g. Redis). `RATE_LIMIT_ENABLED=false` turns it off, and the Gradle `test` task sets that because tests call hundreds of times as the same employee; `RateLimitIntegrationTest` turns it back on with small limits. When adding expensive endpoints (simulations, MCP-facing APIs), give them their own rule.

## Auth server (`auth-server/`)

A separate Spring Boot app (Gradle subproject, `./gradlew :auth-server:bootRun`, port 8081) that is an OAuth 2.1 authorization server (Spring Security 7.1's built-in authorization server, `spring-boot-starter-oauth2-authorization-server`). It owns employee accounts in the `auth` schema of the same Postgres (`AUTH_DB_URL`, default `insur_core_db?currentSchema=auth`; its own Flyway history lives there, so core and auth migrations never mix; V3 adds `oauth2_authorization`, the library schema adapted to Postgres, so codes survive restarts). `SecurityConfig` has three chains: (1) the authorization server endpoints, all under `/auth` so nginx's `/auth/` rule covers them (`/auth/oauth2/authorize|token|jwks|revoke|introspect`, `/auth/userinfo`, `/auth/connect/logout`), plus the standard metadata at `/.well-known/openid-configuration` and `/.well-known/oauth-authorization-server`, which nginx and Vite proxy separately; unauthenticated browser requests are sent to the login page; (2) the stateless Bearer API `/auth/me`, `/auth/password`, `/auth/admin/**` (ADMIN); (3) the session-based screens `/auth/login` (Thymeleaf form, `POST` handled by Spring Security form login with CSRF) and `/auth/password-change`. There is no JSON login API any more; passwords are typed only into the auth server's own page. The one registered client is the staff SPA (`app.oauth.web.*`, client id `insur-web`): public (no secret), authorization code only, PKCE required, no consent screen, exact redirect URIs (`AUTH_WEB_REDIRECT_URIS`, `AUTH_WEB_POST_LOGOUT_URIS`). Spring Authorization Server rejects `localhost` redirect URIs (loopback must be an IP literal), so dev URLs use `127.0.0.1`. Public clients get no refresh token (the library only issues them with DPoP), so the SPA repeats the authorize redirect when the access token expires and the login session (`AUTH_SESSION_TIMEOUT`, default 30m, cookie `INSUR_AUTH_SESSION` on path `/auth`) makes that password-free. Tokens are RS256 with the key from `AUTH_SIGNING_KEY` (PKCS#8 PEM text or file path, 2048+ bits); without it a temporary key is generated at startup, which invalidates tokens on restart and cannot work with several instances, so set it outside dev. Issuer is `AUTH_ISSUER` (the browser-facing origin, default `http://127.0.0.1:8088`, local profile `http://127.0.0.1:5173`) and must equal the core's `AUTH_ISSUER`. `TokenClaimsCustomizer` adds `roles` (array) and `name` to access tokens and `name` to ID tokens; `sub` is the empId. It reloads the employee at every token issue, so a disabled/locked employee or one whose password was reset gets `invalid_grant` (`E-AUTH-103`/`E-AUTH-107` in `error_description`) even with a live login session, and role changes apply from the next token (TTL `JWT_TTL_MINUTES`, default 60). Claims stored in `oauth2_authorization` go through Jackson's allowlist, so use `ArrayList` rather than `List.copyOf`. `EmployeeAuthenticationProvider` wraps `AuthService.authenticate` (unknown empId and wrong password both `E-AUTH-101`, 5 consecutive failures lock with `E-AUTH-102`, disabled `E-AUTH-103`, every attempt in `TB_LOGIN_HIST`); it is a bean only, because also adding it to the chain makes `ProviderManager` retry the parent on failure and count each failure twice. It builds a standard `User` principal (custom classes fail Jackson deserialization) with a `FactorGrantedAuthority` (FACTOR_PASSWORD), which supplies the ID token's `auth_time`. Employees with a temporary password get no login session: `LoginSuccessHandler` stores the empId as pending and redirects to `/auth/password-change`, which changes the password, creates the session and resumes the saved authorize request (redirects use relative paths because the proxied Host may lack the port; `server.tomcat.use-relative-redirects=true`). `/auth/admin/**` (ADMIN) lists, creates, updates (name, dept, roles, active), resets passwords, unlocks, and pages login history; every change is written to `TB_EMP_AUDIT`, and an admin cannot remove their own ADMIN role or disable themselves (`E-EMP-004`). The `local` profile creates dev accounts admin01, agent01, agent02, uw01, op01, clm01 with password `Insur!2026` and shows them on the login page; in other environments `AUTH_BOOTSTRAP_ADMIN_PASSWORD` creates an `admin` account (change required) when no employee exists. The auth server keeps its own copies of the common envelope classes on purpose, since it deploys independently. The authorization server endpoint tests drive the real flow with MockMvc (`AuthIntegrationTest`); the authorize endpoint reads GET parameters from the query string, so tests must put them in the URL rather than `.param()`.

## Frontend (`frontend/`)

React 19 + Vite, plain JavaScript. `npm install` then `npm run dev` (http://127.0.0.1:5173; opening `localhost` jumps to `127.0.0.1` because the auth server rejects `localhost` redirect URIs and tokens live in per-origin `sessionStorage`) proxies `/api` to the core (8080) and `/auth` plus `/.well-known` to the auth server (8081), the same path split nginx does in the container image, so the browser always talks to one origin and no CORS config exists. Login is OAuth 2.1 Authorization Code + PKCE (`src/auth/oauth.js`): the login page redirects to `/auth/oauth2/authorize` with an S256 challenge (verifier and state in `sessionStorage`), `/callback` checks the state, exchanges the code at `/auth/oauth2/token`, then loads `/auth/me` for roles. On expiry or 401 the SPA drops its token (the auth server session usually lets the next login skip the password); the logout button also ends the auth server session through `/auth/connect/logout` with `id_token_hint`. `crypto.subtle` needs a secure context, so deployments other than 127.0.0.1 must be HTTPS. `src/api/http.js` wraps every call in the common envelope and throws `ApiError` (code, message, globalTxId) for non-`0000` responses; screens that change data create one `globalTxId` when the form or dialog opens and reuse it on retry, so a double click or a lost response cannot apply twice. Menus and buttons are hidden by role (`src/common/menu.js`, `hasAny`) but the servers remain the authority. Codes and coverage lists in `src/common/codes.js` mirror the V7/V8 seeds; update them together with new migrations.

## CI

`.github/workflows/ci.yml` runs on pushes and pull requests to `main` and `develop`: `./gradlew test` against a `postgres:16-alpine` service container set to Asia/Seoul (core and auth server), `npm ci && npm run build` in `frontend/`, and, once both pass, `docker build` of the three images (nothing is pushed). The job sets `LC_ALL=C.UTF-8` because the Korean test names become report file names.

## Running everything

Locally: Postgres (`docker compose up -d`), then the core and auth server with `SPRING_PROFILES_ACTIVE=local`, then `npm run dev` in `frontend/` and open http://127.0.0.1:5173. With Docker only: `AUTH_PROFILES=local docker compose --profile app up -d --build` serves the app on http://127.0.0.1:8088 (the services under the `app` profile do not start with a plain `docker compose up -d`); the core fetches the auth server's JWKS at `http://auth:8081/auth/oauth2/jwks`, `JWT_SECRET` is optional (only for dev HS256 tokens), and `AUTH_SIGNING_KEY` keeps tokens valid across auth server restarts. If the browser uses another origin, set `AUTH_ISSUER` and `AUTH_WEB_*_URIS` to it. `./gradlew test` runs both the core and the auth server tests, and both need the database.

## Schema migrations

Flyway owns the schema. Migrations go in `src/main/resources/db/migration` as `V<n>__<description>.sql` and run automatically at startup. Hibernate is set to `ddl-auto=validate`, so every entity change needs a matching migration or the app fails on startup. Never edit a migration that has already been applied; add a new one instead. Every table and column carries a Korean `COMMENT ON` (core V22, auth V4) so DB tools such as DBeaver show its meaning; a migration that adds a table or column must add its comments in the same file, and `SchemaCommentTest` (core and auth server) fails on any table or column without one (Flyway's history table excepted). Comments state code values and units the way the entity Javadoc does; keep the two consistent. Boot 4 only auto-configures Flyway through `spring-boot-starter-flyway`, so don't swap it for bare `flyway-core`. `flyway-database-postgresql` is required for Postgres support.

## Premium rating policy

`PremiumService.quote` requires the rating factors marked required in `TB_PRM_FACTOR_POLICY` (effective-dated by 보험시기, managed via `/api/admin/premium/policy-list|policy-revise`, ADMIN to revise). Missing ones fail with `E-PRM-005`, in both quote and apply. Sample seed: car DRIVER_AGE + DISCOUNT_GRADE, fire STRUCTURE_GRADE, so test/e2e requests need a neutral rating (age 35 / grade 3 = factor 1.0). `scripts/e2e-check.sh --cleanup` restores the seeded policy rows.
