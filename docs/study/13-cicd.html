CI/CD와 배포

사람이 손으로 빌드하고 서버에 올리면 언젠가 실수가 납니다. CI/CD는 코드가 합쳐지고 운영에 나가기까지의 과정을 자동화해서, 매번 같은 절차로 검증하고 배포하게 만드는 일입니다.

CI와 CD

뜻목표
CI (지속적 통합)코드를 올릴 때마다 자동으로 빌드하고 테스트한다깨진 코드가 main에 들어오지 않게 한다
CD (지속적 전달)통과한 결과물을 언제든 배포할 수 있는 상태로 만든다. 운영 배포는 사람이 승인배포를 버튼 하나로 만든다
CD (지속적 배포)통과하면 운영까지 자동으로 나간다사람 손을 완전히 뺀다

핵심은 "같은 일을 매번 똑같이"입니다. 빌드가 개발자 PC에서만 되는 상태라면 그 PC가 사라지는 날 배포도 멈춥니다.

파이프라인의 단계

  • 앞 단계가 실패하면 뒤로 가지 않습니다. 빠르고 싼 검사를 앞에 둡니다.
  • 한 번 빌드한 결과물을 끝까지 씁니다. 개발 환경에 올린 JAR(또는 이미지)과 운영에 올릴 것이 같아야, 개발에서 검증한 게 운영에서도 의미가 있습니다. 환경마다 다시 빌드하지 않습니다.
  • 결과물에는 버전이나 커밋 해시를 붙여 "운영에 지금 무엇이 떠 있는지" 바로 알 수 있게 합니다.

예시: GitHub Actions로 테스트 돌리기

GitHub Actions는 저장소의 .github/workflows/ 아래 YAML 파일로 파이프라인을 정의합니다. 아래는 이 프로젝트에 맞춰 쓴 예시입니다. 이 프로젝트의 테스트는 실제 PostgreSQL이 필요해서, CI에서도 DB 컨테이너(서비스 컨테이너)를 함께 띄웁니다.

그대로 쓰기 전에 이 YAML은 설명용이고 실제로 실행해 보지 않았습니다. 액션 버전과 DB 설정은 도입할 때 확인하세요. CI용 DB 비밀번호는 테스트 전용 값이라 예시에 그대로 적었지만, 운영 비밀값은 절대 YAML에 쓰지 않고 저장소의 Secrets 설정에 넣어 ${{ secrets.이름 }}으로 읽습니다.

머지를 지키는 장치

  • 브랜치 보호: main에 직접 push를 막고, PR과 리뷰 승인, CI 통과를 머지 조건으로 겁니다.
  • 필수 검사: 테스트, 빌드, 정적 분석(코드 품질), 의존성 취약점 검사를 필수 체크로 지정합니다.
  • 빠른 피드백: CI가 30분씩 걸리면 아무도 기다리지 않습니다. 캐시(Gradle 의존성 캐시)를 쓰고, 느린 테스트는 분리합니다.
  • 불안정한 테스트: 가끔 실패하는 테스트를 "다시 돌리면 되겠지"로 넘기면 CI를 아무도 믿지 않게 됩니다. 원인을 찾아 고칩니다.

배포 방식

방식방법장점비용
롤링서버를 한 대씩 새 버전으로 교체추가 자원이 거의 없음교체 중 구·신 버전이 섞여 돎
블루그린새 환경을 통째로 띄우고 트래픽을 한 번에 전환되돌리기가 즉시 가능잠시 자원이 두 배
카나리일부 사용자에게만 먼저 새 버전을 보내고 지표를 보며 늘림문제를 작은 범위에서 발견트래픽 분배와 모니터링 장치가 필요

어떤 방식이든 헬스 체크(새 서버가 정상인지 확인하는 주소)가 있어야 트래픽을 넘길지 판단할 수 있습니다.

DB 마이그레이션과 배포 순서

  • Flyway처럼 앱이 기동할 때 마이그레이션을 실행하면 편하지만, 서버 여러 대가 동시에 기동하면 누가 먼저 실행할지 신경 써야 합니다. Flyway는 DB 잠금으로 한 번만 실행되게 합니다.
  • 롤링 배포 중에는 구버전 서버가 새 스키마 위에서 잠시 돕니다. 그래서 스키마 변경은 구버전 코드와도 호환되게 만듭니다. (실무 도구 12의 "나눠서 배포")
  • 코드는 롤백할 수 있어도 이미 실행된 마이그레이션은 자동으로 되돌아가지 않습니다. 되돌리는 SQL을 미리 준비하거나, 되돌릴 필요가 없는 추가형 변경으로 설계합니다.

컨테이너와 환경

  • 도커 이미지는 앱과 실행 환경(자바 버전, OS 라이브러리)을 한 묶음으로 만들어, 어디서든 같은 방식으로 돌게 합니다. 스프링 부트는 실행 가능한 JAR(bootJar)을 만들고, 이를 이미지에 담습니다.
  • 설정은 이미지 밖에서: 같은 이미지를 개발·운영에 쓰고, 차이는 환경변수와 비밀 관리 서비스로 주입합니다.
  • 환경 단계: 로컬 → 개발 → 스테이징(운영과 최대한 같은 환경) → 운영. 운영에 가까울수록 배포 승인이 엄격해집니다.

배포 후에 할 일

  1. 헬스 체크와 오류율, 응답 시간 지표를 확인합니다. 배포 직후가 문제가 가장 잘 드러나는 때입니다.
  2. 이상이 보이면 고치려 하기 전에 먼저 되돌립니다. 원인 분석은 서비스를 살린 뒤에 합니다.
  3. 배포한 버전과 변경 내용을 기록합니다(릴리스 노트, Git 태그). 다음 장애 때 "언제부터 이랬나"를 찾는 단서가 됩니다.
이 프로젝트에서는 아직 CI 설정(.github/workflows/)이 없습니다. 빌드는 Gradle 래퍼(./gradlew)로 하고, 테스트 태스크가 테스트 전용 JWT_SECRET과 Asia/Seoul 시간대를 직접 넣습니다. 그래서 CI에서 따로 챙길 것은 PostgreSQL만 남습니다. 운영 JWT_SECRET은 기본값이 없어 설정하지 않으면 기동에 실패하므로, 배포 환경에서 비밀 설정이 빠지면 바로 드러납니다. API 문서(Swagger)는 기본으로 꺼져 있어 운영에서 실수로 열리지 않습니다. 스키마는 앱 기동 시 Flyway가 적용합니다.

스스로 점검

개발 환경과 운영 환경에 올리는 JAR을 각각 따로 빌드하면 어떤 문제가 있나요?

빌드 시점의 의존성이나 소스가 달라질 수 있어서, 개발에서 검증한 것과 운영에 나간 것이 같다고 보장할 수 없습니다. 한 번 빌드한 결과물을 승격시켜 씁니다.

배포 직후 오류율이 치솟았다면 먼저 할 일은?

이전 버전으로 되돌려 서비스를 살리는 것입니다. 원인 분석은 그다음입니다.

롤링 배포에서 컬럼 이름을 한 번에 바꾸면 왜 위험한가요?

교체 중에 아직 남은 구버전 서버가 옛 컬럼 이름으로 쿼리해서 실패합니다. 새 컬럼 추가부터 옛 컬럼 삭제까지 여러 번에 나눠 배포해야 합니다.

운영 비밀번호를 CI YAML에 적으면 안 되는 이유는?

YAML은 저장소에 커밋되어 이력에 영원히 남고, 저장소에 접근하는 누구나 볼 수 있습니다. 저장소의 Secrets 설정을 씁니다.
