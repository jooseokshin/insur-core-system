트랜잭션과 동시성

혼자 쓸 땐 멀쩡하던 코드가 여러 사람이 동시에 쓰면 깨집니다. 돈과 계약을 다루는 백엔드에서 가장 중요한 주제입니다.

트랜잭션과 ACID

트랜잭션은 여러 작업을 하나로 묶어 "전부 성공하거나 전부 취소"되게 하는 단위입니다. 계좌 이체에서 출금만 되고 입금이 안 되면 안 되는 것과 같습니다.

성질뜻
원자성 (Atomicity)전부 반영되거나 전부 취소된다
일관성 (Consistency)끝났을 때 제약과 규칙이 지켜진 상태다
격리성 (Isolation)동시에 도는 트랜잭션이 서로 영향을 주지 않는 것처럼 보인다
지속성 (Durability)커밋된 결과는 장애가 나도 남는다

스프링에서의 트랜잭션

  • 보통 서비스 메서드 단위로 @Transactional을 붙입니다. 업무 하나가 한 트랜잭션이 되게 합니다.
  • 기본적으로 언체크 예외(RuntimeException)가 나면 롤백하고, 체크 예외는 롤백하지 않습니다. 체크 예외에도 롤백하려면 설정이 필요합니다.
  • 예외를 catch해서 삼키면 스프링이 실패를 모르고 커밋해 버립니다.
  • 이메일 발송이나 외부 API 호출처럼 되돌릴 수 없는 일을 트랜잭션 안에서 하면, 이후에 롤백돼도 이미 나간 건 되돌릴 수 없습니다. 커밋 이후에 하거나 별도 장치(이벤트, 아웃박스)로 보냅니다.
  • 트랜잭션은 짧게 유지합니다. 오래 열어 두면 DB 잠금과 연결을 붙잡아 전체가 느려집니다.

동시에 쓰면 생기는 문제

현상설명
Dirty read다른 트랜잭션이 아직 커밋하지 않은 값을 읽는다
Non-repeatable read같은 행을 두 번 읽었는데 그 사이 다른 트랜잭션이 바꿔서 값이 달라진다
Phantom read같은 조건으로 두 번 조회했는데 새 행이 끼어들어 결과 건수가 달라진다
Lost update둘이 같은 값을 읽고 각자 수정해 저장하면, 나중 저장이 앞선 수정을 덮어쓴다

격리 수준은 이런 현상을 얼마나 막을지 정하는 단계입니다. 높을수록 안전하지만 느려집니다. PostgreSQL의 기본은 Read Committed(커밋된 값만 읽음)입니다. 이 수준에서도 lost update는 막히지 않으므로, "읽고 → 판단하고 → 쓰는" 로직은 별도 장치가 필요합니다.

충돌을 다루는 세 가지 방법

  • 비관적 락: "충돌이 날 것"이라 보고 읽을 때부터 행을 잠급니다(SELECT ... FOR UPDATE). 다른 트랜잭션은 기다립니다. 충돌이 잦고 정확성이 중요할 때 좋지만, 대기와 교착(deadlock)을 조심해야 합니다.
  • 낙관적 락: "충돌이 드물 것"이라 보고 잠그지 않습니다. 행에 버전 번호를 두고, 저장할 때 읽었을 때의 버전과 같을 때만 반영합니다. 다르면 실패시켜 다시 시도하게 합니다.
  • DB 제약에 맡기기: 유니크 제약을 걸어 두면 두 요청이 동시에 같은 키를 넣어도 DB가 한 건만 통과시키고 나머지는 오류로 돌려줍니다. 가장 단순하고 확실합니다. 코드의 "있는지 먼저 확인"은 보조일 뿐이고, 제약이 최종 방어선입니다.
교착(deadlock) A는 1번 행을 잠그고 2번을 기다리고, B는 2번 행을 잠그고 1번을 기다리면 둘 다 영원히 멈춥니다. 여러 행을 잠글 때는 항상 같은 순서로 잠그세요.

멱등성: 두 번 와도 한 번처럼

네트워크는 신뢰할 수 없습니다. 요청이 서버에 도착했는데 응답이 중간에 유실되면, 클라이언트는 실패로 보고 같은 요청을 다시 보냅니다. 이때 같은 일이 두 번 일어나면 안 됩니다. 구현의 기본 틀은 이렇습니다.

  1. 요청마다 고유한 멱등성 키(거래 ID)를 받는다.
  2. 그 키로 이미 처리한 기록이 있으면, 새로 처리하지 않고 처음 결과를 그대로 돌려준다.
  3. 같은 키로 내용이 다른 요청이 오면 거절한다. 실수나 악용일 수 있기 때문이다. (요청 내용의 지문(해시)을 저장해 비교)
  4. 동시에 같은 키가 두 번 들어와도 DB 유니크 제약으로 한 건만 저장되게 한다. 진 쪽은 충돌 오류를 받고, 다시 보내면 첫 결과를 받는다.

분산 환경에서는

서비스가 여러 개로 나뉘어 DB도 따로 쓰면, 하나의 트랜잭션으로 묶는 것이 어렵거나 불가능합니다. 이때는 최종적 일관성을 받아들이고, 실패 시 앞선 작업을 되돌리는 보상 작업(사가 패턴), 메시지를 DB와 함께 안전하게 보내는 아웃박스 같은 기법을 씁니다. 처음부터 이렇게 시작할 필요는 없지만, 이름과 목적은 알아 두세요.

이 프로젝트에서는 청약 접수(applyContract)는 하나의 트랜잭션입니다. 채번, 계약 저장, 담보 저장, 상태 이력 기록이 한 묶음이라 중간에 실패하면 채번까지 롤백되어 결번이 생기지 않습니다. globalTxId가 멱등성 키이고, 같은 키 재전송은 첫 결과를 돌려주며, 다른 내용이면 E-CTR-019(409), 동시에 들어온 쪽은 유니크 제약 위반을 E-CTR-011(409)로 바꿉니다. 요청 내용은 SHA-256 지문으로 비교합니다. 상태 변경은 SELECT ... FOR UPDATE(비관적 락)로 계약 행을 잠가, 두 요청이 같은 현재 상태를 보고 서로 덮어쓰는 일을 막습니다. 이 동작은 동시성 테스트(스레드 6개가 같은 키로 동시 요청)로 확인합니다.

스스로 점검

이체 처리 중 예외가 났는데 데이터가 반쯤 반영돼 있다면 무엇을 의심하나요?

예외를 catch해서 삼켜 스프링이 커밋했거나, 트랜잭션 경계가 없거나, 체크 예외라서 롤백되지 않은 경우를 의심합니다. 같은 클래스 내부 호출로 @Transactional이 적용되지 않았을 수도 있습니다.

"있는지 확인하고 없으면 저장"만으로 중복을 못 막는 이유는?

두 요청이 동시에 "없음"을 확인하면 둘 다 저장합니다. 확인과 저장 사이에 틈이 있기 때문입니다. 유니크 제약이나 락으로 막아야 합니다.

비관적 락과 낙관적 락은 언제 각각 쓰나요?

같은 데이터에 충돌이 잦고 틀리면 큰 손해인 경우는 비관적 락, 충돌이 드물고 처리량이 중요하며 실패 시 재시도가 가능한 경우는 낙관적 락을 고려합니다.

같은 멱등성 키로 내용이 다른 요청이 오면 왜 거절하나요?

첫 결과를 돌려주면 클라이언트는 자기가 보낸 새 내용이 처리됐다고 착각합니다. 클라이언트의 실수를 드러내는 것이 안전합니다.
