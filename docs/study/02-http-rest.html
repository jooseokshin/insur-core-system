개념 02기초

HTTP와 REST

API는 서버가 세상과 맺는 약속입니다. HTTP가 어떻게 말하는지, 좋은 API는 어떤 모양인지, 실패는 어떻게 알려야 하는지를 다룹니다.

HTTP 요청과 응답

HTTP는 요청과 응답으로만 이루어진 단순한 프로토콜입니다. 요청은 네 부분으로 구성됩니다.

  • 메서드: 무엇을 하려는지 (GET, POST, PUT, PATCH, DELETE)
  • 경로: 어떤 대상인지 (/api/contract/apply)
  • 헤더: 부가 정보. 인증 토큰(Authorization), 본문 형식(Content-Type) 등
  • 바디: 보내는 데이터. 보통 JSON

응답은 상태코드, 헤더, 바디로 이루어집니다. 클라이언트는 상태코드만 보고도 성공인지 실패인지, 누구 잘못인지 알 수 있어야 합니다.

메서드의 의미: 안전성과 멱등성

메서드마다 약속된 성질이 있습니다. 이 성질을 알면 재시도를 안전하게 설계할 수 있습니다.

메서드쓰임안전(데이터를 안 바꿈)멱등(여러 번 해도 결과 같음)
GET조회예예
PUT전체 교체아니오예
PATCH일부 수정아니오구현에 따라 다름
DELETE삭제아니오예
POST생성, 처리 실행아니오아니오

POST는 기본적으로 멱등하지 않아서, 네트워크가 끊겨 재전송하면 같은 주문이나 계약이 두 번 만들어질 수 있습니다. 그래서 결제나 계약처럼 중요한 POST에는 멱등성 키를 둡니다. 요청마다 고유한 ID를 실어 보내고, 서버가 같은 ID를 이미 처리했는지 확인해 한 번만 실행하는 방식입니다. 개념 07에서 이어서 다룹니다.

상태코드로 말하기

코드의미언제 쓰나
200 / 201성공 / 생성됨정상 처리
400잘못된 요청값 형식·범위 오류, 검증 실패
401인증 안 됨토큰이 없거나 만료·위조

404대상 없음존재하지 않는 자원
409충돌현재 상태와 맞지 않음, 중복 요청
429너무 많은 요청호출 한도 초과

401과 403을 헷갈리지 마세요 401은 "누구인지 모르겠다", 403은 "누구인지는 알지만 허용되지 않는다"입니다. 4xx는 클라이언트가 고칠 수 있는 오류, 5xx는 서버가 책임져야 하는 오류입니다.

REST 스타일 설계

REST는 "자원(명사)을 URL로 표현하고, 행위는 HTTP 메서드로 표현한다"는 설계 방식입니다.

  • 좋은 예: GET /contracts/123, POST /contracts, DELETE /contracts/123
  • 피할 예: /getContract, /deleteContract (동사가 경로에 들어감)
  • 컬렉션은 복수형, 목록은 필터와 페이지로 좁힙니다. GET /contracts?status=20&page=0&size=20
  • 하위 자원은 경로로 표현합니다. /contracts/123/coverages

현실에서는 REST를 엄격히 지키지 않는 곳도 많습니다. "계약을 해지한다"처럼 자원 하나의 수정으로 딱 떨어지지 않는 업무 행위는 POST /contracts/123/terminate 같은 동작형 경로로 두기도 합니다. 중요한 것은 팀 안에서 일관되게 쓰는 것입니다.

좋은 API의 습관

  • 일관된 오류 응답: 성공이든 실패든 같은 모양으로 오류코드와 메시지를 내려 클라이언트가 한 가지 방식으로 처리하게 합니다.
  • 내부 사정 숨기기: 스택 트레이스나 SQL 오류를 응답에 노출하지 않습니다. 자세한 내용은 로그에만 남깁니다.
  • 페이징: 목록은 항상 상한이 있어야 합니다. 수백만 건을 한 번에 돌려주면 서버와 네트워크가 먼저 무너집니다.
  • 버전 관리: 응답 모양을 바꿀 때 기존 클라이언트가 깨지지 않도록 /v1/ 같은 버전이나 하위 호환 규칙을 둡니다.
  • DTO 분리: DB 엔티티를 그대로 내보내면 내부 구조가 외부 계약이 되어 바꾸기 어려워집니다. 요청과 응답 전용 객체를 따로 둡니다.
  • 문서화: OpenAPI(Swagger)로 명세를 자동 생성하면 문서와 코드가 어긋나지 않습니다.
이 프로젝트에서는 모든 API가 POST이고, 요청과 응답이 header(거래 UUID, 사번, 응답코드)와 body로 이루어진 "공통 전문" 형태입니다. 금융·보험 시스템에서 흔한 방식입니다. 오류는 E-CTR-010 같은 업무 오류코드와 함께 400·404·409·500 상태코드로 내려가고, 인증 실패는 E-AUTH-001(401), 권한 부족은 E-AUTH-002(403)입니다. Swagger UI로 API 명세를 볼 수 있습니다.

스스로 점검

같은 POST를 두 번 보내면 왜 문제가 되고, 어떻게 막나요?

POST는 멱등하지 않아 재전송 시 같은 처리가 두 번 일어날 수 있습니다. 요청마다 고유한 멱등성 키를 보내고, 서버가 이미 처리한 키는 새로 실행하지 않고 첫 결과를 돌려줍니다.

다른 사람의 계약을 조회했을 때 403과 404 중 무엇이 나을까요?

403은 "그 계약이 존재한다"는 사실을 알려 줍니다. 존재 여부 자체를 숨기고 싶다면 없는 것과 똑같이 404로 답하는 편이 안전합니다. 이 프로젝트가 택한 방식입니다.

목록 API에 페이징이 꼭 필요한 이유는?

데이터가 늘어나면 한 번에 모두 내려주는 순간 메모리, DB, 네트워크가 한계에 닿기 때문입니다. 상한을 두어 응답 크기를 예측 가능하게 만듭니다.
