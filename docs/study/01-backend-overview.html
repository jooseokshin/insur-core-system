개념 01기초

백엔드의 큰 그림

백엔드는 화면 뒤에서 규칙을 지키고, 데이터를 안전하게 보관하고, 요청에 정확히 답하는 일을 맡습니다. 세부 기술을 배우기 전에 전체 구조부터 잡습니다.

백엔드가 하는 일

앱이나 웹 화면(클라이언트)은 사용자가 보는 부분이고, 백엔드(서버)는 그 요청을 받아 처리하는 부분입니다. 서버는 크게 네 가지를 책임집니다.

  • 검증: 들어온 값이 올바른지, 보낸 사람에게 권한이 있는지 확인합니다.
  • 업무 규칙: 서비스가 지켜야 하는 정책(가격 계산, 상태 전이, 한도 등)을 적용합니다.
  • 저장: 결과를 데이터베이스에 남겨 서버가 꺼져도 사라지지 않게 합니다.
  • 응답: 성공과 실패를 약속된 형식으로 돌려줍니다.

서버는 클라이언트를 믿지 않는 것이 기본입니다. 화면에서 이미 검사했더라도 서버는 다시 검사합니다. 화면은 우회할 수 있기 때문입니다.

요청 하나의 여정

사용자가 버튼을 누르면 요청이 아래 순서로 지나갑니다. 각 단계는 한 가지 일만 하도록 나눕니다.

응답은 같은 길을 거꾸로 돌아갑니다. 어느 단계에서든 문제가 생기면 그 자리에서 멈추고 오류 응답으로 바뀝니다.

계층맡은 일하지 말아야 할 일
컨트롤러요청을 받아 서비스에 넘기고 응답으로 바꿉니다업무 규칙 판단, DB 직접 접근

역할이 섞이면 바꿀 때마다 여러 곳을 고쳐야 하고, 테스트하기도 어려워집니다. 예를 들어 가격 계산이 컨트롤러에 있으면 배치나 다른 API에서 같은 계산을 쓸 수 없습니다.

상태 없는 서버 (Stateless)

요청마다 필요한 정보를 모두 담아 보내고, 서버는 이전 요청을 기억하지 않는 방식입니다. 서버를 여러 대로 늘려도 어느 서버가 받든 결과가 같아서 확장이 쉽습니다. 로그인 상태를 서버 메모리에 두면 이 장점이 사라지므로, 토큰처럼 요청에 실려 오는 방식을 많이 씁니다. 자세한 내용은 개념 08에서 다룹니다.

코드 밖의 요구사항(비기능 요건)

기능이 동작하는 것만으로는 부족합니다. 실무에서는 다음 항목이 설계를 좌우합니다.

  • 정합성: 돈과 계약처럼 틀리면 안 되는 데이터가 항상 맞아야 합니다. (개념 07)
  • 보안: 누가, 무엇을 할 수 있는지를 통제합니다. (개념 08)
  • 성능: 응답 시간과 동시에 처리하는 양입니다. (개념 05, 06)
  • 가용성: 일부가 고장 나도 서비스가 계속 되는 정도입니다.
  • 관측 가능성: 문제가 생겼을 때 로그와 지표로 원인을 찾을 수 있어야 합니다. (개념 09)
이 프로젝트에서는 패키지가 controller, service, domain, common으로 나뉘어 있습니다. 컨트롤러는 요청 바디를 서비스에 넘기고 응답을 감싸는 일만 하고, 보험료 검증이나 상태 전이 같은 규칙은 서비스와 도메인에 있습니다. 보안·예외 처리·로깅처럼 모든 요청에 공통인 것은 common에 모여 있습니다.

스스로 점검

클라이언트에서 이미 검증했는데 서버가 또 검증하는 이유는?

클라이언트는 사용자가 마음대로 우회하거나 직접 요청을 만들어 보낼 수 있기 때문입니다. 서버 검증이 진짜 방어선입니다.

가격 계산을 컨트롤러에 두면 어떤 문제가 생길까요?

다른 진입점(배치, 다른 API)에서 재사용할 수 없고, 웹 계층 없이는 테스트하기 어렵습니다. 업무 규칙은 서비스나 도메인에 둡니다.

서버를 stateless로 만들면 무엇이 좋아지나요?

서버를 늘리거나 교체해도 요청 결과가 같아서 수평 확장과 배포가 쉬워집니다.
