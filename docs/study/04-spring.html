개념 04기초

스프링 핵심

스프링은 "객체를 대신 만들고 연결해 주는" 프레임워크입니다. 이 한 문장을 이해하면 어노테이션 대부분이 같은 원리로 보입니다.

제어의 역전(IoC)과 의존성 주입(DI)

보통은 내가 필요한 객체를 직접 new로 만듭니다. 스프링에서는 스프링이 객체를 만들어 보관하고(컨테이너), 필요한 곳에 넣어 줍니다. 만드는 책임이 개발자에서 프레임워크로 넘어가서 "제어의 역전"이라고 부릅니다. 이렇게 넣어 주는 것이 의존성 주입입니다.

이점은 세 가지입니다.

  • 구현을 바꿔도 사용하는 쪽 코드를 고치지 않아도 됩니다.
  • 테스트에서 진짜 대신 가짜 객체를 넣을 수 있습니다.
  • 객체의 생성과 수명을 한곳에서 관리합니다.

주입 방법은 생성자, 필드, 세터가 있는데 생성자 주입을 권장합니다. 필요한 의존성이 없으면 객체가 아예 만들어지지 않아 실수가 일찍 드러나고, 필드를 final로 둘 수 있습니다.

빈(Bean)과 스테레오타입

컨테이너가 관리하는 객체를 빈이라고 합니다. 클래스에 역할 어노테이션을 붙이면 스프링이 찾아서 빈으로 등록합니다.

어노테이션역할
@RestControllerHTTP 요청을 받는 컨트롤러, 반환값을 JSON으로 응답
@Service업무 규칙을 담는 서비스
@Repository데이터 접근
@Component그 밖의 일반 빈 (필터 등)
@Configuration + @Bean직접 만든 객체나 외부 라이브러리 객체를 빈으로 등록하는 설정
빈은 기본적으로 싱글톤입니다 한 애플리케이션에 객체가 하나뿐이고 모든 요청이 공유합니다. 그래서 빈의 필드에 요청별 상태를 두면 안 됩니다. (개념 03)

자동 설정과 스타터

스프링 부트는 의존성을 보고 필요한 설정을 알아서 합니다. 예를 들어 JPA 스타터와 DB 드라이버를 추가하면 DB 연결, 트랜잭션 관리자가 자동으로 구성됩니다. 필요한 부분만 application.properties로 덮어씁니다. 이를 "설정보다 관례"라고 합니다. 자동으로 되는 것이 많은 만큼, 문제가 생겼을 때는 "어떤 설정이 자동으로 적용됐는지"를 의심하세요.

부트 메이저 버전이 바뀌면 스타터 이름이나 패키지 위치가 바뀌는 경우가 있어서, 버전 업 때는 공식 마이그레이션 가이드를 먼저 확인합니다.

설정 외부화와 프로파일

  • 환경마다 다른 값(DB 주소, 비밀키)은 코드에 박지 않고 환경변수나 설정 파일에서 읽습니다.
  • ${DB_URL:기본값} 형태로 "환경변수가 있으면 그것, 없으면 기본값"을 쓸 수 있습니다.
  • 프로파일(local, dev, prod)로 환경별 설정 묶음을 나눕니다.
  • 비밀번호와 키는 저장소에 올리지 않습니다. 운영 비밀값의 기본값을 코드에 두는 것도 피합니다. 값이 없으면 기동이 실패하게 두면 설정 누락을 배포 즉시 발견합니다.

AOP와 프록시: @Transactional이 동작하는 방식

AOP는 여러 곳에 공통으로 필요한 부가 기능(트랜잭션, 로깅, 권한 확인)을 업무 코드와 분리하는 기법입니다. 스프링은 대상 객체를 감싸는 프록시를 만들어, 메서드 호출 전후에 부가 기능을 끼워 넣습니다. @Transactional이 붙은 메서드를 부르면 실제로는 프록시가 먼저 트랜잭션을 시작하고, 원래 메서드를 실행한 뒤, 정상이면 커밋하고 예외가 나면 롤백합니다.

같은 클래스 안에서 부르면 프록시를 거치지 않습니다 클래스 안의 메서드 A가 같은 클래스의 @Transactional 메서드 B를 호출하면 프록시를 거치지 않아 B의 어노테이션이 적용되지 않습니다. 이 자기 호출 함정은 면접과 실무 모두에서 자주 나옵니다. 메서드 접근 제어자가 private일 때도 적용되지 않습니다.

필터, 인터셉터, 예외 처리기의 위치

요청이 컨트롤러에 닿기 전후에 끼어드는 장치가 여러 개 있어서 헷갈리기 쉽습니다.

장치위치주로 쓰는 일
서블릿 필터스프링 MVC 바깥(가장 앞)인증, 로깅 초기화·정리, 인코딩
인터셉터컨트롤러 호출 전후공통 권한 검사, 실행 시간 측정
@RestControllerAdvice컨트롤러에서 던진 예외를 받는 곳예외를 일관된 오류 응답으로 변환

필터 단계에서 터진 오류는 컨트롤러 예외 처리기에 닿지 않기 때문에, 인증 실패 응답은 따로 처리해야 합니다.

이 프로젝트에서는 서비스 클래스는 @Service와 롬복의 @RequiredArgsConstructor로 final 필드 생성자 주입을 받습니다. 업무 시각의 기준인 Clock은 @Configuration 클래스의 @Bean으로 등록해 필요한 곳에 주입합니다. 설정은 DB_URL, JWT_SECRET 같은 환경변수로 받고, 비밀키는 기본값이 없어 설정하지 않으면 기동이 실패합니다. 개발용으로만 쓰는 local 프로파일이 따로 있습니다. 예외는 @RestControllerAdvice가 모아 공통 전문으로 응답하고, 필터 단계의 인증 오류는 보안 설정에서 직접 응답을 씁니다.

스스로 점검

DI가 왜 테스트에 도움이 되나요?

의존 객체를 밖에서 넣어 주기 때문에, 테스트에서는 DB나 외부 시스템 대신 가짜 객체를 넣어 해당 클래스만 검증할 수 있습니다.

@Transactional 메서드를 같은 클래스의 다른 메서드에서 호출하면 트랜잭션이 안 걸리는 이유는?

트랜잭션은 프록시가 메서드 호출을 가로채서 걸어 줍니다. 같은 객체 안의 호출은 프록시를 거치지 않으므로 어노테이션이 무시됩니다.

비밀키의 기본값을 코드에 넣지 않는 이유는?

기본값이 저장소에 남으면 누구나 볼 수 있고, 설정을 깜빡한 운영 환경이 알려진 키로 조용히 돌아갈 수 있습니다. 값이 없으면 기동 실패하게 하는 편이 안전합니다.
