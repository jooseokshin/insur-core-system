손해보험 기간계 청약 처리 구조

자동차보험(01)과 일반화재보험(02)의 청약을 받아 증권번호와 청약번호를 채번하고, 계약 원장과 담보를 한 트랜잭션으로 저장한 뒤 조회할 수 있는 1차 코어 로직입니다. 모든 요청은 JWT 인증을 거치고, 같은 거래 UUID(globalTxId)의 재전송은 중복 저장하지 않습니다. 계층은 controller → service → domain → DB 순서로 내려가고, 공통 전문·인증·로그 처리는 common 패키지가 맡습니다.

  • 엔드포인트 POST /api/contract/apply · /inquiry · /list · /status-change · /status-history · /endorse · /endorse-history · /renew · /renew-quote · /payment · /payment-history · /api/premium/quote · /api/admin/premium/*
  • 인증 JWT Bearer (HS256) · 역할 인가 4개
  • 테이블 10개 (Flyway V1 ~ V18)
  • 테스트 215건 통과
  • API 문서 /swagger-ui.html · /v3/api-docs (springdoc, local 프로파일에서만 켜짐)
  • 번호 형식 POL-CAR-2026-000001

계층 구조

어떤 클래스가 어느 계층에 있고 누구를 호출하는지 보여줍니다. 채번기만 JPA를 거치지 않고 JdbcTemplate으로 채번 테이블을 직접 갱신합니다.

보험료 산출과 요율 관리 구조

보험료를 계산하는 쪽(PremiumService)과 요율표를 고치는 쪽(PremiumAdminService)은 컨트롤러부터 서비스까지 나뉘어 있고, 요율·계수·필수 계수 정책 테이블을 함께 씁니다. 계약 서비스는 청약 대조, 갱신, 해지 환급에서 이 계산을 가져다 씁니다.

청약 요청 처리 순서

한 건의 청약이 저장되기까지 오가는 호출입니다. 파란 막대 구간이 하나의 트랜잭션이라서 중간에 실패하면 채번까지 함께 롤백되고 결번이 생기지 않습니다.

테이블 구조

V1__create_contract_tables.sql로 생성되고, V2__add_contract_global_tx_id.sql이 멱등성용 GLOBAL_TX_ID 컬럼을, V3__create_contract_status_history.sql이 상태 변경 이력 테이블을, V4__add_contract_reg_emp_id.sql이 청약 접수 사번(REG_EMP_ID)을 더합니다. V4는 V3 이후 접수한 계약의 접수 사번을 이력의 최초 기록에서 채우고, 그 이전 계약은 NULL로 남깁니다. V5__add_contract_list_indexes.sql은 목록 조회의 최근 접수순 정렬과 접수자별 목록을 받치는 인덱스 두 개(SYS_REG_DT, REG_EMP_ID + SYS_REG_DT)를, V6__add_contract_req_hash.sql이 청약 요청 내용의 지문(REQ_HASH, SHA-256)을, V7__create_premium_rate.sql이 담보별 요율표(TB_PRM_RATE)와 샘플 요율을, V8__create_premium_factor.sql이 요율 계수표(TB_PRM_FACTOR)를, V9__add_contract_rating_info.sql이 청약 때 쓴 요율 계수 입력값 컬럼을, V10__add_premium_effective_period.sql이 요율/계수의 적용 기간(EFF_FROM~EFF_TO)을, V11__add_contract_termination_refund.sql이 해지일과 환급보험료를, V12__create_contract_endorsement.sql이 계약 변경(배서) 이력 테이블(TB_CTR_ENDORSE)을, V13__guard_premium_period_overlap.sql이 요율/계수의 적용 기간이 겹치면 DB가 거절하는 트리거를, V14__create_premium_audit.sql이 요율/계수 관리 감사 이력(TB_PRM_AUDIT)을, V15__create_premium_factor_policy.sql이 필수 계수 정책(TB_PRM_FACTOR_POLICY)과 샘플 정책을, V16__allow_policy_audit_target.sql이 감사 이력의 대상 종류에 POLICY를, V17__add_contract_renewal_link.sql이 갱신 계약의 원 계약 증권번호(RENEWED_FROM)와 계약당 유효한 갱신 하나만 허용하는 부분 유니크 인덱스(청약취소 제외)를, V18__create_contract_payment.sql이 납입(수납) 내역 테이블(TB_CTR_PAYMENT)을 더합니다. 금액 컬럼은 원 단위 NUMERIC(15, 0)이고 엔티티에서는 BigDecimal로 다룹니다.

보험료 산출

POST /api/premium/quote는 보험종목, 보험기간, 요율 계수 입력, 담보별 가입금액으로 담보별 보험료와 총보험료를 계산해 돌려줍니다. 아무것도 저장하지 않으며, 응답의 담보별 보험료와 총보험료를 청약 요청에 그대로 넣으면 청약 접수의 보험료 검증을 통과합니다. 청약 접수는 같은 계산으로 담보별 보험료를 다시 구해 대조하므로(불일치는 400 E-CTR-020), 산출 API의 결과를 그대로 쓰는 것이 청약이 통과하는 가장 확실한 방법입니다. 이미 접수된 거래의 재전송은 요율표를 다시 조회하지 않아서, 접수 이후 요율이 바뀌어도 기존 결과를 돌려줍니다.

요율 개정(적용 기간) — 요율과 계수 행마다 적용 기간(EFF_FROM ~ EFF_TO, 양 끝 포함, EFF_TO가 비어 있으면 현재까지 유효)이 있고, 보험시기에 적용되는 행으로 계산합니다. 개정할 때는 기존 행을 지우거나 고치지 말고 기존 행의 EFF_TO를 닫은 뒤 새 행을 추가하는 새 마이그레이션(V<n>)을 만듭니다. 적용 기간이 겹치는 행(같은 담보, 같은 계수 키, 겹치는 연령 구간)은 DB 트리거가 거절합니다. 보험시기에 적용되는 요율이 없는 담보는 400 E-PRM-001이고, 가입금액이 0 이하이거나 소수·15자리 초과면 400 E-CTR-007입니다.

요율/계수 관리

요율표와 계수표를 코드 배포나 마이그레이션 없이 개정하는 API입니다(/api/admin/premium). 조회(rate-list, factor-list, policy-list, audit-list)는 심사·계약 관리·ADMIN, 개정과 신규 등록(rate-revise, factor-revise, policy-revise)은 ADMIN만 할 수 있습니다. 요율과 계수는 적용 기간으로 이력을 관리하므로, 개정은 기존 행을 고치거나 지우지 않고 가장 최근 행의 적용 종료일을 (새 시작일 − 1일)로 닫은 뒤 새 행을 추가합니다. 같은 보험종목·담보코드(계수는 같은 칸)가 없으면 새로 만듭니다(CREATE). 모든 변경은 감사 이력(TB_PRM_AUDIT)에 남고, audit-list로 대상 종류(RATE·FACTOR·POLICY), 대상 식별 앞부분, 처리 사번, 처리일 범위(서울 기준)를 조합해 최근 처리순으로 페이지(기본 20, 최대 100) 단위 조회할 수 있습니다. 조건 오류는 400 E-ADM-001, 페이징 오류는 400 E-CTR-016입니다.

규칙내용
적용 시작일오늘(서울 기준) 이후여야 합니다. 과거 일자를 바꾸면 이미 나간 견적과 맞지 않게 되므로 400 E-ADM-002. 같은 칸의 가장 최근 행(예약된 미래 행 포함)의 시작일보다 늦어야 하며, 아니면 409 E-ADM-003

목록 응답의 각 행에는 오늘 기준 상태가 붙습니다: ACTIVE(적용 중), FUTURE(적용 예정), CLOSED(종료). 이 API는 조회 API가 아니라 관리용이라 페이징이 없고 개정 이력 전체를 한 번에 돌려줍니다. 개정으로 이미 접수된 계약의 보험료가 바뀌지는 않습니다(청약 재전송은 요율표를 다시 조회하지 않음). 새 요율이 적용되는 것은 보험시기가 새 시작일 이후인 보험료 산출과 청약부터입니다.

역할별 권한

외부 인증 서버가 발급한 JWT의 roles 클레임이 ROLE_ 권한으로 바뀝니다. API별 허용 역할은 SecurityConfig의 URL 규칙이 정하고, 상태 변경은 변경하려는 상태에 따라 ContractAccessPolicy가 한 번 더 확인합니다. 권한이 없으면 403 E-AUTH-002 전문으로 응답하고 서비스는 호출하지 않습니다.

조회 범위(데이터 단위 권한) — 청약 접수 담당(AGENT)만 가진 사용자는 본인이 접수한 계약(REG_EMP_ID = 토큰의 sub)만 조회할 수 있고, 다른 사람이 접수한 계약은 존재하지 않는 계약과 똑같이 404 E-CTR-010으로 응답해 존재 여부를 알 수 없게 합니다. 심사·계약 관리·ADMIN 역할이 하나라도 있으면 전체를 조회합니다. 다른 사번이 접수한 거래 UUID로 청약을 재전송하면 그 계약의 번호를 알려주지 않고 409 E-CTR-015로 거절합니다.

계약 목록 조회

POST /api/contract/list는 조건에 맞는 계약을 한 페이지씩 돌려줍니다. 조건은 모두 선택이며, 입력한 것만 AND로 적용합니다. 기본 정렬은 최근 접수순(접수 일시 → 증권번호 내림차순)이고, 접수일·보험시기·총보험료 기준으로 오름차순/내림차순을 고를 수 있습니다. 같은 값끼리는 증권번호를 같은 방향으로 정렬해 페이지 경계가 흔들리지 않습니다. 행에는 계약 요약만 담고 담보는 계약 조회(/inquiry), 이력은 상태 이력 조회(/status-history)로 확인합니다. 청약 접수 담당(AGENT)만 가진 사용자는 어떤 조건을 써도 본인이 접수한 계약만 목록에 나오고, 목록에서는 남의 계약이 오류가 아니라 그냥 빠집니다.

범위 조건의 시작이 종료보다 크거나 총보험료 최소가 음수면 400 E-CTR-017입니다. 증권번호/청약번호 앞부분 일치는 기본키와 유니크 인덱스를 탈 수 있지만, 총보험료·보험시기 정렬과 범위는 전용 인덱스가 없어 계약이 많아지면 인덱스 추가를 검토해야 합니다.

계약 상태 전이

POST /api/contract/status-change가 계약상태(CTR_STAT_CD)를 아래 순서로만 바꿉니다. 해지와 청약취소는 종료 상태라 더 바꿀 수 없고, 허용되지 않는 전이(같은 상태로의 변경 포함)는 409 E-CTR-014로 거절합니다. 같은 계약의 변경이 동시에 들어오면 행을 잠그고(SELECT … FOR UPDATE) 한 번에 하나씩 처리하므로, 서로 배타적인 변경 중 하나만 성공합니다. 변경이 성공하면 변경 전/후 상태, 처리 사번(JWT subject), 거래 UUID를 TB_CTR_STAT_HIST에 남기고, POST /api/contract/status-history로 페이지 단위로 조회합니다. 계약 조회(/inquiry) 응답에는 이력을 담지 않으므로, 이력이 필요하면 이 API를 따로 호출합니다. 요청은 {contractNo, page, size}이며 page는 0부터, 생략하면 0페이지 20건입니다. 페이지 크기는 1~100이고 벗어나면 400 E-CTR-016입니다. 응답은 items(오래된 순)와 totalElements, totalPages를 담고, 범위를 벗어난 페이지는 빈 목록으로 응답합니다. 조회 범위는 계약 조회와 같습니다.

청약(10) ──→ 유효(20) ──→ 해지(30)   청약 승인 · 해지
   └──────────→ 청약취소(90)          성립 전 취소/거절

재전송 안전 — 상태 변경과 배서는 같은 계약에서 같은 거래 UUID로 이미 처리한 요청이 다시 오면(응답을 못 받은 재전송) 다시 바꾸지 않고 처음 결과를 돌려줍니다. 같은 거래 UUID로 다른 내용을 요청하면 409 E-CTR-019로 거절합니다. 이력에 남은 거래 UUID를 근거로 판단하므로 별도 저장소는 없습니다.

해지 환급보험료 — 해지(30)로 바꿀 때 해지일(서울 기준 오늘)과 환급보험료를 계약에 기록하고 응답에 담습니다. 환급보험료 = 총보험료 × 남은 일수 ÷ 보험기간 일수(원 단위 반올림)이며, 남은 일수 = 보험종기 − max(해지일, 보험시기)입니다. 보험시기 전에 해지하면 전액, 보험종기 이후에 해지하면 0원이고, 단기요율 같은 해지 공제는 적용하지 않습니다. 환급 금액은 조회 응답(termDate, refundPremium)으로도 확인할 수 있습니다.

납입(수납) — POST /api/contract/payment는 청약(10) 상태의 계약에 보험료를 나누어 낼 수 있게 합니다(계약 관리 담당과 ADMIN). 낸 합계가 총보험료에 이르러야 심사 담당이 승인(유효, 20)할 수 있고, 미납이면 409 E-CTR-028입니다. 계약 행을 잠근 채 남은 보험료를 계산하므로 동시 납입도 초과되지 않으며, 남은 보험료를 넘으면 409 E-CTR-027, 청약 상태가 아니면 409 E-CTR-026, 지원하지 않는 납부 방법(CASH·TRANSFER·CARD 외)은 400 E-CTR-029입니다. 같은 거래 UUID의 재전송은 한 번만 반영하고 처음 결과를 돌려주며, 내용이 다르면 E-CTR-019, 다른 사번이면 E-CTR-015입니다. 납입 내역은 /payment-history로 오래된 순 페이지 조회하며 낸 합계와 남은 보험료가 함께 나옵니다(AGENT는 본인 접수 계약만). 이 단계에서는 청약취소나 해지의 환급 지급 기록은 아직 없습니다.

계약 갱신 — POST /api/contract/renew는 유효(20) 계약을 보험종기 60일 전부터 보험종기까지(서울 기준) 갱신해 새 청약(10)을 만듭니다. 보험시기는 원 계약의 보험종기이고 기간 길이는 원 계약과 같으며(년/월 단위면 같은 년/월), 계약자·피보험자·담보·가입금액을 이어받습니다. 담보 보험료는 갱신 시점의 요율표와 필수 계수 정책으로 다시 산출하며, 요율 계수는 요청의 rating 또는 원 계약에 저장된 값을 씁니다(필수 계수가 늘었으면 400 E-PRM-005이므로 rating으로 채웁니다). 응답에 원 계약과 갱신 계약의 총보험료가 함께 나옵니다. 유효 상태가 아니면 409 E-CTR-023, 갱신 가능 기간이 아니면 409 E-CTR-024, 이미 갱신했으면 409 E-CTR-025이며 갱신 계약이 청약취소되면 다시 갱신할 수 있습니다. 같은 거래 UUID의 재전송은 요율이 바뀌었어도 처음 결과를 돌려주고, 다른 원 계약이면 E-CTR-019, 다른 사번이면 E-CTR-015입니다. 동시에 같은 계약을 갱신하면 DB 부분 유니크 인덱스가 막아 한쪽만 성공합니다. AGENT는 본인이 접수한 계약만 갱신할 수 있습니다. 갱신 전에 POST /api/contract/renew-quote로 미리 볼 수 있습니다. 아무것도 저장하지 않고 갱신과 같은 검증·권한·산출을 거치며, 갱신 보험기간과 담보별·총 보험료를 원 계약과 비교해 증감(premiumDifference)과 적용 계수를 보여 줍니다. rating을 바꿔 보내 보험료를 비교해 본 뒤 같은 요청으로 갱신하면 그 보험료가 됩니다.

계약 변경(배서) — POST /api/contract/endorse는 청약(10) 또는 유효(20) 상태의 계약에서 계약자와 피보험자를 바꿉니다. 현재 값과 같은 항목은 바뀐 것으로 보지 않고, 바뀐 항목이 하나도 없으면 400 E-CTR-022, 해지·청약취소 계약은 409 E-CTR-021로 거절합니다. 바뀐 항목마다 변경 전/후 값, 처리 사번, 거래 UUID가 TB_CTR_ENDORSE에 쌓이고 POST /api/contract/endorse-history로 페이지 단위로 조회합니다(조회 범위는 계약 조회와 같음). 보험료와 담보는 바꾸지 않습니다.
