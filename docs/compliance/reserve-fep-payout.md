# IBNR·지급준비금 결산, FEP, 펌뱅킹 지급과 대사

- 작성일: 2026-11-12
- 대상: V27(스프링 배치 실행 이력), V28(지급준비금 결산), V29(FEP·지급·대사), 배치 작업 `reserveCloseJob`·`payoutReconJob`
- 성격: 구현 설명과 근거 정리다. **법률·계리 의견이 아니고, 전문 규격·응답코드·은행 계좌는 실제 값이 아니다.**
- 출처 표기: **[공식]** 정부·감독기관 자료, **[보도]** 언론·업계 자료. 원문으로 다시 확인해야 한다.

## 1. IBNR 과 지급준비금

### 왜 필요한가

손해율 분석은 지금까지 접수된 사고만 센다. 사고가 난 날과 보험회사가 아는 날(접수), 돈을 다 낸 날(지급) 사이에는 시차가 있어서 최근 기간일수록 손해가 작게 보이고, 그대로 요율을 정하거나 이익을 계산하면 틀린다. 이미 났지만 아직 모르는(또는 덜 진전된) 손해를 추정해 부채로 쌓아 두는 것이 IBNR 이다.

| 구분 | 뜻 | 이 시스템 |
|---|---|---|
| 개별추산액 | 접수됐지만 아직 지급하지 않은 사고의 추정액 | 손해사정 완료면 지급 예정액, 접수만 됐으면 청구액 |
| IBNR | 이미 발생했지만 아직 청구되지 않은 사고의 향후 지급 추정액 [보도: [뉴스토마토](https://newstomato.com/ReadNews.aspx?no=1209289)] | 지급 기준 진전 삼각형으로 추정 (아래) |
| 지급준비금 | 개별추산액 + IBNR | 분기 결산 배치가 종목별로 확정 (`TB_RSV_CLOSE`) |

IFRS17 에서는 이 몫이 발생사고부채(LIC)에 해당한다 [자료: [CAS IFRS 17 Study Note](https://casact.org/sites/default/files/2021-09/6I_IFRS_Study_Note.pdf)]. 감독 기준은 손해진전계수(LDF)를 보험금 지급의무 발생일, 타당성을 입증하면 원인사고일 기준으로 산출하도록 2023년 시행세칙을 보완했다 [보도: [머니투데이방송](https://news.mtn.co.kr/news-detail/2023122511311733966)]. 이 시스템은 사고일(`ACDT_DT`) 기준으로 삼각형을 만든다.

### 계산 (`ChainLadder`, `ReserveService`)

```
삼각형: 사고 기간(분기·연) × 경과(지급일이 사고 기간 뒤 몇 번째 기간인지), 값 = 누적 지급액
체인래더   f_k = Σ C(i,k+1) ÷ Σ C(i,k),  CDF = f_a × … × 꼬리,  최종 = 지급 × CDF
BF         최종 = 지급 + 기대손해율 × 경과보험료 × (1 − 1/CDF)
케이프코드  기대손해율 = Σ지급 ÷ Σ(경과보험료 ÷ CDF)    (입력하지 않으면 실적에서 구한다)
IBNR       = 최종 − 지급 − 개별추산액,  진전율(1/CDF) 50% 이상은 체인래더, 미만은 BF,  적립은 음수를 0 으로
```

최근 사고 기간은 지급이 적어 CDF 를 곱하면 크게 흔들린다. BF 는 아직 지급되지 않을 몫만 기대손해율로 채워서 덜 흔들린다. 50% 기준과 음수를 0 으로 두는 처리는 이 시스템의 판단 기준이며 회사마다 다르다.

손 계산 예(시험 `ReserveIbnrFixture`, 보험종목 98, 2001년 분기): f1 = 50,000 ÷ 20,000 = 2.5 → 2001Q4 진전율 40% 라 BF, 케이프코드 기대손해율 = 52,000 ÷ 309,800 = 16.79%, BF 최종 = 2,000 + 0.1679 × 92,000 × 0.6 = 11,268, IBNR = 11,268 − 2,000 − 8,000 = 1,268, 지급준비금 = 8,000 + 1,268 = 9,268.

### 넣지 않은 것 (실무에서 더 해야 하는 일)

- 접수 기준(보고) 삼각형과 발생손해액 삼각형: 과거 시점의 개별추산액 이력이 없어 지급 기준만 쓴다. 사정 금액 이력을 남기면 발생손해 삼각형을 만들 수 있다.
- 대형 사고 분리, 물가·추세 조정, 손해조사비, 할인과 위험조정(IFRS17), 재보험 출재분
- 진전계수 선택(평균 종류, 이상치 제외)에 대한 계리 판단, 꼬리 계수 추정

## 2. 결산과 대사를 왜 스프링 배치로 하나

| 작업 | 방식 | 이유 |
|---|---|---|
| 분기 지급준비금 결산 (`reserveCloseJob`) | 스프링 배치 | 기준일당 한 번만 확정해야 한다. 식별 파라미터(`closeDate`)가 같은 완료 인스턴스는 배치가 다시 실행하지 않는다(E-BAT-002). 실패하면 같은 파라미터로 재시작한다. 실행 기록(`BATCH_*`)이 감사 증적이 된다 |
| 일일 지급 대사 (`payoutReconJob`) | 스프링 배치 + 매일 06:30 예약 | 은행 내역 받기 → 비교 두 단계, 단계별 읽기·쓰기·걸러냄 건수가 남는다. 다시 해야 할 일이 많아 `run.id` 로 같은 날도 다시 실행할 수 있게 했다 |
| 신용정보원 전송, 이체·결과 조회, 회선 확인 | `@Scheduled` 큐 처리 | 건별로 짧게 끝나고 계속 도는 일이라 배치 인스턴스로 관리할 이유가 없다 |

서버가 여러 대면 예약 실행이 대수만큼 돈다. 한 대에서만 켜거나 ShedLock 같은 분산 잠금을 붙여야 한다(지금은 없음).

## 3. FEP (대외계 중계)

금융회사 시스템은 계정계·정보계·대외계·채널로 나누어 설명된다 [자료: [우체국금융 차세대 RFI](https://www.smallake.kr/wp-content/uploads/2019/09/차세대-우체국금융시스템-구축을-위한-정보제공요청서RFI.pdf)]. FEP 는 대외계에서 기관마다 다른 연결을 한곳에 모아 공통 기능을 하는 중계 계층이다. 이 시스템의 `FepGateway` 가 하는 일:

| 기능 | 왜 | 구현 |
|---|---|---|
| 개시·종료 (망관리 0800/0810, N001/N002) | 기관 정기 점검 시간에 전문을 보내지 않게 한다. 종료 중 업무 전문은 "보내지 않음"으로 끝나 대기열·지급이 대기로 남는다 | `TB_FEP_INST.SIGN_ON_YN`, `/api/admin/fep/sign-on|sign-off` |
| 회선 확인 (에코, N003) | 업무 없이 회선이 살아 있는지 주기적으로 본다 | 60초마다 예약 실행, 성공하면 회선 차단을 푼다 |
| 회선 차단 (서킷 브레이커) | 죽은 기관에 요청을 계속 걸면 스레드·연결이 묶여 장애가 번진다 | 응답 없음 연속 5번이면 60초 차단 (서버별 메모리) |
| 전문 로그 | 기관과 장애를 따질 때 추적번호로 서로 찾는다. 업무가 롤백돼도 기관에는 이미 갔으므로 로그는 남아야 한다 | `TB_FEP_MSG_LOG` 를 별도 트랜잭션으로. 본문은 개인정보라 길이와 SHA-256 만 |
| "보냈는지 모름" 구분 | 응답 없음(기관이 처리했을 수 있음)과 FEP 가 보내지 않음(안전하게 다시 보내도 됨)을 나눈다 | `ExternalAgencyException.isMaybeDelivered()` |

공통부 60바이트(전문길이·종별·거래구분·기관코드·일시·추적번호·응답코드)는 이 프로젝트가 정한 모양이고 실제 기관 규격이 아니다. 실제 공동망 규약은 전자금융공동망업무 시행세칙 같은 기관 문서로 받는다 [자료: [전자금융공동망업무 시행세칙](https://www.smallake.kr/wp-content/uploads/2019/02/전자금융공동망업무-시행세칙2018.12.4.pdf)].

## 4. 펌뱅킹 지급

펌뱅킹은 회사와 은행 전산을 전용회선이나 VAN 으로 직접 연결해 이체·조회를 하는 서비스다 [자료: [하나은행 펌뱅킹 안내](https://www.kebhana.com/cont/info/info03/info0308/info030801/index.jsp)]. 지금까지 사고 지급(40)은 "지급 결정"까지였고 돈이 실제로 나가는 부분이 없었다.

| 단계 | 왜 | 구현 |
|---|---|---|
| 예금주 조회 | 잘못된 계좌로 보낸 돈은 돌려받기 어렵다. 계좌 상태(해지·지급정지)와 예금주가 맞는지 먼저 확인한다 [자료: [알체라](https://www.alchera.ai/resource/blog/ekyc-foreign-insurance-benefit-account-verification)] | B100. 요청할 때 반드시 하고, 이름이 다르면 E-PAY-003 |
| 금액은 원천에서 | 화면이 금액을 정하면 조작·실수가 들어온다 | 사고 지급액 합계(40) 또는 마일리지 환급액(20) |
| 계좌번호 암호화 | 은행에 평문으로 보내야 하므로 해시가 아니라 복호화 가능한 암호화 | AES-256-GCM, 키 `ACCOUNT_ENC_KEY`, 화면은 마스킹 값 |
| **결과 불명 처리** | 이체 요청에 응답이 없으면 은행이 처리했는지 모른다. 그대로 다시 보내면 이중 지급이 될 수 있다 | 응답 없음 → 결과 불명(70) → 30초 뒤 **결과 조회**(B300). S면 완료, F면 실패, N(받은 적 없음)이면 같은 거래고유번호로 다시 이체 |
| 원천당 하나 | 같은 보험금을 두 번 요청하지 못하게 | 실패(80)가 아닌 지급은 원천당 하나 (부분 유니크 인덱스) |

모의 은행 계좌: `004-11122233344` 홍길동(정상), `004-55566677777` 김지급(이체 후 응답 유실 → 결과 불명인데 실제로는 이체됨), `088-12345678888` 이불명(받기 전 끊김 → 결과 조회 N), `020-99900011122` 해지, `011-30012345678` 지급정지.

### 대사

은행 응답만 믿으면 놓치는 사고(응답 유실, 우리 상태 오류, 은행 쪽 중복)가 있다. 매일 은행 이체 내역과 지급 원장을 거래고유번호로 맞춰 본다.

| 결과 | 뜻 | 할 일 |
|---|---|---|
| MATCHED | 일치 | 없음 |
| STATUS_DIFF | 은행은 이체했는데 우리는 결과 불명·실패 | **이중 지급 위험**. 실패로 보고 다시 지급하면 안 된다 |
| OURS_ONLY | 우리는 완료인데 은행 내역 없음 | 은행 확인. 자정 전후 건은 다음 날 대사에서 일치할 수 있다 |
| BANK_ONLY | 은행에만 있음 | 원장 누락 조사 |
| AMOUNT_DIFF | 금액 다름 | 은행 확인 |

대사는 비교와 보고만 하고 지급 상태는 바꾸지 않는다(상태 해소는 결과 조회가 한다).

## 5. 찾아봤지만 이번에 넣지 않은 것 (다음 후보)

| 항목 | 내용 |
|---|---|
| 보험료 자동이체(CMS) | 금융결제원 CMS 로 계약자 계좌에서 보험료를 출금. 출금 요청 파일 → 결과 파일 반영 → 미납 처리. 전형적인 대량 배치 |
| 가상계좌 입금 통지 | 은행이 입금을 실시간 통지 → 수납 처리 (수신 전문) |
| 회계 분개 연계 | 수납·지급·준비금 적립을 총계정원장(GL) 분개로 넘기는 인터페이스 |
| 재보험 정산 | 출재 보험료·보험금 정산서 |
| 분산 잠금 | 예약 작업을 여러 서버에서 한 번만 돌게 하는 장치 (ShedLock 등) |
